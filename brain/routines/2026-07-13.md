### deferred — Dreams (research preview): model support extended to Claude Fable 5 and Claude Sonnet 5
- URL: https://platform.claude.com/docs/en/release-notes/overview (July 10, 2026 entry)
- Source: Claude Platform release notes, published 2026-07-10
- Theme: 5 (Self-improvement loops) and 4 (Persistent memory + context)
- Touches: `csis/dreams/pipeline.py` (currently a full mock — see its own docstring: `"Phase-0 doesn't actually call Anthropic Dreams; it simulates the candidate-store production locally... per brain/research/01-anthropic-sdk.md so swapping the real backend in later is a thin wrapper."`), and directly answers `ROADMAP.md` P1.1 ("Real Dreams API integration · next up ... once it's accessible to the operator")
- Size: large
- Risk: medium — new external dependency (real API calls, cost, latency) and a real architecture bridge, not just a wrapper swap
- Design sketch: I fetched the full Dreams API reference today (`POST /v1/dreams`, `dreaming-2026-04-21` + `managed-agents-2026-04-01` beta headers). The real API's shape matches what `brain/research/01-anthropic-sdk.md` anticipated — a `dream` resource with `inputs: [memory_store, sessions]`, async `pending → running → completed/failed/canceled` lifecycle, and an `output` memory store that never mutates the input. But it is **not** a drop-in replacement for `DreamPipeline.schedule()`: the real API operates on **Claude Managed Agents `memory_store` and `session` resources**, while CSIS's memory tiers (`csis/memory/store.py`) are local JSON-backed candidate/live stores with no Managed Agents session concept. A real integration needs a translation layer — e.g. a `csis/dreams/managed_agents_bridge.py` that (a) serializes a tier's candidate entries into a temporary Managed Agents memory store, (b) uploads recent event-log session transcripts (or synthesizes session-shaped input, since CSIS doesn't run on Managed Agents sessions today), (c) polls the dream to completion under the existing `CadenceBudget` gate, (d) reads the output store back and maps it through the existing `score_candidate()` / `redact_for_partial()` quality gates before it's eligible for `promote()`. The chokepoint this should hang off is `DreamPipeline.schedule()` itself (same call site, swapped `_model` for a real network client) — not a new parallel path — so the F4/F10 mitigations (partial-output redaction, per-tier cadence) keep applying unchanged.
- Why deferred: Managed Agents (and Dreams specifically) require gated research-preview access via a request form, plus an `ANTHROPIC_API_KEY` with that scope — an external dependency this routine can't provision. The translation layer is also genuinely new architecture (local JSON store ↔ Managed Agents memory store), which is squarely "medium or larger" and risk above low per the routine's own bar, not a same-day PR. Recommend this becomes the concrete implementation plan for ROADMAP P1.1 whenever Managed Agents access is available to the operator.
