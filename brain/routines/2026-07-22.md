### deferred — Managed Agents `memory_store.*` / `environment.*` lifecycle webhooks

- URL: https://platform.claude.com/docs/en/managed-agents/webhooks#supported-event-types
- Source: platform.claude.com/docs, published 2026-07-22
- Theme: 4 — Persistent memory + context
- Touches: `csis/memory/store.py` (`MemoryStore.promote()` / `mark_verified()`), `csis/substrate/event_log.py`
- Size: medium
- Risk: medium (promote() sits one call away from the promotion CAS chokepoint)
- Design sketch: CSIS's dashboard is poll-only today ("reads from on-disk artifacts... polls every 2s"). Managed Agents ships the push equivalent — subscribe to `memory_store.entry_promoted` / `memory_store.entry_deprecated`-shaped events instead of tailing a file. A CSIS analogue would add an optional callback list on `MemoryStore` that `promote()` invokes *after* the CAS succeeds (never before — a callback that could raise or block must not sit inside the atomic section). Needs a design pass on whether callback failures should be swallowed, logged, or tripwire-worthy, and a regression test proving the callback fires exactly once per successful promotion (not per attempt) even under the contention path `test_promote_serialization_under_contention` exercises.
- Why deferred: touches code adjacent to the promotion CAS; the cycle-9 lesson ("chokepoints beat perimeters") means this needs its own scrutiny pass rather than a same-day PR.

## Operational note (not part of the seven-theme scan, but load-bearing)

Before scanning, this run checked the repo's actual PR history via the GitHub MCP server (`state=all`, sorted by creation date) to reconstruct what prior runs had already covered, since `brain/routines/index.md` on `main` is still the original placeholder row from PR #7. What that turned up:

**Every routine-opened PR since the routine went live is still open, as a draft, unmerged — over 100 of them, from #8 (2026-05-23) through #111 (2026-07-21).** The only routine-related PR that has ever merged is #7, the one that installed the routine itself. This includes at least one confirmed duplicate: `tripwire-severity-score` was opened as its own PR on both 2026-07-01 and 2026-07-02 with the same slug, one day apart — the "check existing PRs before pushing a branch" step in the routine either wasn't run that day or didn't catch it.

Two consequences worth knowing about:

1. **The ledger never advances.** `brain/routines/index.md` and every `YYYY-MM-DD.md` log only exist on unmerged branches; a fresh clone of `main` (which is what every run gets) sees none of them. Two months of "read state first" is effectively "read an empty ledger" every single day. Prior runs seem to have partially compensated by re-deriving coverage from PR history in-session (PR #45's body says as much: *"Index.md carries forward all prior unmerged log-branch entries for dedup continuity"*) — but that's a workaround, not something `main` reflects, and this run had to redo the same reconstruction from scratch.
2. **Nothing the routine has proposed has actually reached the codebase in two months of daily runs**, other than the routine's own bootstrap. If the intent was for a human to periodically review and merge the queue, that review doesn't appear to be happening — the queue is >100 drafts deep and growing by roughly one PR a day.

This run did not attempt to fix the backlog (out of scope for a single daily run, and merging/closing a hundred old PRs unilaterally is exactly the kind of action that needs a human decision, not an automated one). Flagging it here, and via the routine's out-of-band summary, so a person can decide whether to start merging the queue, prune it, or change how the routine ships its output.
